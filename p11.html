    AGENTES¶

    Hasta este punto, los sistemas descritos funcionan de forma lineal o reactiva: el usuario lanza una consulta, el sistema recupera información y genera una respuesta en un único recorrido. Este enfoque es válido para tareas simples, pero se queda corto cuando el problema requiere varios pasos, comprobaciones intermedias o decisiones adaptativas. Un Agente rompe esa linealidad y añade capacidad de razonamiento iterativo.

    Un Agente es un sistema en el que el LLM no se limita a generar texto, sino que actúa como un motor de decisión que opera dentro de un bucle de retroalimentación. El modelo puede planificar una acción, ejecutar una herramienta, observar el resultado y, en función de esa observación, decidir el siguiente paso. Este ciclo se repite hasta que el agente considera que ha alcanzado un estado suficiente para producir una respuesta final o completar la tarea.

    Diferencia entre Pipeline y Agente

    Pipeline (Flujo rígido): Sigue una secuencia predefinida del tipo Pregunta → Clasificación → RAG → Respuesta. Cada etapa depende estrictamente de la anterior, por lo que un error temprano, como una mala clasificación, se propaga y compromete todo el resultado. Es simple, predecible y fácil de mantener, pero poco flexible.

    Agente (Flujo dinámico): Funciona como un proceso adaptativo: Pregunta → ¿Qué herramientas necesito? → [Ejecuta Tool A] → ¿Es suficiente? → No, necesito Tool B → [Ejecuta Tool B] → ¿Es suficiente? → Sí → Respuesta.

    El modelo evalúa continuamente el estado del problema y ajusta su estrategia, lo que le permite manejar tareas complejas, ambiguas o abiertas de forma más robusta.

    Los agentes están en desarrollo, lo que denominamos agentes independientes.

    Arquitecturas de Razonamiento¶

    Para que un agente basado en LLMs sea realmente eficaz, no basta con que tenga acceso a herramientas. Es necesario que siga una metodología explícita de razonamiento, que le permita descomponer problemas, evaluar resultados intermedios y decidir el siguiente paso de forma coherente. Estas metodologías definen cómo “piensa” el agente y condicionan directamente su fiabilidad y capacidad para resolver tareas complejas.

    Chain of Thought (CoT) – Cadena de Pensamiento:

    La Chain of Thought consiste en inducir al modelo a razonar en varios pasos antes de producir la respuesta final. En lugar de saltar directamente a una conclusión, el modelo genera razonamientos intermedios que conectan la pregunta con la respuesta. Este enfoque ha demostrado reducir de forma significativa los errores en problemas lógicos, matemáticos o de múltiples condiciones. En el contexto de un agente, el CoT aparece cuando el modelo justifica internamente por qué elige una herramienta, descarta otra o considera que aún no tiene información suficiente.

    ReAct (Reasoning + Acting)

    ReAct combina razonamiento y acción en un único bucle iterativo, y se considera el enfoque más robusto para agentes prácticos. El modelo alterna entre pensar y actuar, ajustando su estrategia en función de lo que va observando. El ciclo típico es:

    • Thought (Pensamiento): El modelo analiza el estado actual del problema y decide el siguiente paso.

    • Action (Acción): Selecciona y ejecuta una herramienta concreta.

    • Observation (Observación): Recibe el resultado de la acción ejecutada.

    • Repetición: Con esa nueva información, vuelve a razonar y decide si continuar o finalizar.

    Este enfoque permite al agente corregir errores, explorar alternativas y adaptarse dinámicamente a resultados inesperados.

    Plan-and-Execute

    En problemas especialmente largos o complejos, razonar paso a paso puede no ser suficiente. En estos casos, Plan-and-Execute separa el proceso en dos fases claras: primero, el agente construye un plan global con todos los pasos necesarios para resolver la tarea; después, ejecuta cada paso de forma secuencial. Esta estrategia reduce el riesgo de desviaciones, mantiene la coherencia a largo plazo y es especialmente útil en tareas con dependencias claras entre pasos, como flujos de trabajo técnicos o procesos empresariales complejos.

    Componentes Críticos del Agente del Curso¶

    En la práctica del curso, el agente se enfrenta a un dominio especialmente complejo: la normativa laboral, caracterizada por múltiples fuentes, excepciones y comparativas entre convenios. Para manejar esta complejidad de forma fiable, el agente incorpora varios componentes de orquestación que van más allá de un simple flujo de pregunta y respuesta.

    Selección Multi-Fuente (Multi-PDF Routing)

    A diferencia de escenarios más simples, donde una pregunta se resuelve consultando un único documento, aquí el agente debe detectar cuándo una consulta requiere comparar o cruzar información de varias fuentes. Por ejemplo, al preguntar por diferencias salariales entre dos convenios, no basta con recuperar un solo PDF.

    En estos casos, el agente debe identificar todas las fuentes relevantes, generar una lista de herramientas a invocar y coordinar su ejecución. Posteriormente, tiene que agregar y normalizar los resultados, asegurándose de que la comparación se basa en fragmentos equivalentes y coherentes entre documentos distintos.

    Evaluación de Suficiencia del Contexto

    Un agente robusto no responde siempre; también sabe cuándo debe detenerse. Para ello, se implementa una lógica que evalúa tanto la cantidad como la calidad del contexto recuperado. No todos los textos devueltos por un sistema de búsqueda son útiles ni relevantes.

    Si el contexto es insuficiente, por ejemplo fragmentos demasiado cortos, irrelevantes o inconexos, el agente aborta la generación de la respuesta. Este mecanismo actúa como una barrera de seguridad frente a las alucinaciones, priorizando la ausencia de respuesta antes que una respuesta incorrecta.

    Memoria y Estado

    Para razonar de forma coherente, el agente necesita mantener un estado interno que registre sus acciones y decisiones. Esto se articula en dos niveles complementarios.

    La memoria de corto plazo almacena los resultados de las herramientas ejecutadas durante el turno actual, permitiendo al agente reutilizar información sin repetir llamadas innecesarias.

    La trazabilidad se materializa en un registro detallado de cada paso del razonamiento, de modo que un auditor humano pueda reconstruir qué herramientas se usaron, qué información se obtuvo y por qué se tomó cada decisión.

    En conjunto, estos componentes convierten al agente en un sistema controlado, explicable y apto para entornos profesionales donde la fiabilidad es tan importante como la respuesta final.

    El Bucle de Control y el Manejo de Errores¶

    Un agente sin mecanismos de control es un riesgo operativo. En un entorno de producción, donde el agente actúa de forma semiautónoma, es imprescindible introducir salvaguardas explícitas que limiten su comportamiento y eviten respuestas incorrectas o ciclos ineficientes.

    El límite de iteraciones impide que el agente quede atrapado en bucles infinitos, como repetir búsquedas infructuosas sobre la misma fuente. De este modo, se garantiza un coste computacional acotado y un comportamiento predecible.

    La validación de salida actúa como una última capa de seguridad antes de mostrar la respuesta al usuario. Puede consistir en reglas o scripts que detecten inconsistencias, afirmaciones prohibidas o respuestas excesivamente largas que, en realidad, no aportan información verificable.

    El fallback estratégico ofrece una vía de escape controlada. Si el agente no logra determinar la fuente correcta o falla en su razonamiento principal, el sistema da un paso atrás y ejecuta una estrategia más general, como una búsqueda amplia en todos los documentos disponibles, evitando así el bloqueo total del proceso.

    Razonamiento Multi-fuente y Síntesis

    El mayor desafío de un agente NLP no es recuperar información, sino sintetizarla correctamente. Cuando intervienen múltiples convenios o documentos, el agente no puede limitarse a concatenar fragmentos de texto sin contexto.

    Debe analizar posibles contradicciones entre fuentes, detectar matices y excepciones, y estructurar la respuesta de acuerdo con la intención del usuario, por ejemplo, presentando comparativas claras cuando así se solicita. Además, es fundamental mantener la atribución de la información, indicando de forma comprensible qué datos proceden de cada PDF. Esta capacidad de síntesis es lo que transforma datos dispersos en conocimiento útil.

    Ética y Responsabilidad del Agente

    Otorgar autonomía a un agente implica asumir una responsabilidad técnica y ética. En dominios sensibles como el legal o académico, la fiabilidad y la explicabilidad son tan importantes como la respuesta en sí.

    La transparencia exige que el usuario sepa en todo momento que interactúa con un sistema que toma decisiones de búsqueda y razonamiento.

    La auditoría convierte los registros de ejecución en algo más que una herramienta de depuración: son la evidencia de cómo el sistema llegó a una conclusión concreta, un requisito clave en entornos regulados.

    La abstención, lejos de ser un fallo, es una respuesta correcta cuando no existe información suficiente o fiable. Un agente bien diseñado debe priorizar decir “no puedo encontrar evidencia suficiente en los documentos proporcionados” antes que generar una respuesta plausible pero incorrecta.

    Práctica¶

    Objetivo:

    Transformar el pipeline en un agente controlado y deliberativo que decide qué pasos ejecutar y en qué orden, integra varios convenios cuando procede, evalúa la suficiencia del contexto antes de responder, se abstiene si no hay base sólida y deja trazabilidad completa. El resultado es un sistema auditado, no un chatbot.

    Implementación del agente en Python

    Construir un script sobre la práctica anterior que orqueste: recepción de la pregunta, selección de convenios, recuperación de contexto por convenio, evaluación de suficiencia, generación o abstención, validación final y registro íntegro del proceso. El modelo decide los pasos, no el resultado. Memoria y trazabilidad

    El agente debe conservar historial de preguntas, convenios seleccionados, decisiones de abstención y respuestas finales, registrando cada paso para auditoría, evaluación y depuración. Un tercero debe poder reconstruir el razonamiento completo.

    Reglas estrictas de comportamiento

    No puede responder sin contexto suficiente, mezclar convenios sin declararlo, inferir información ausente ni ocultar incertidumbre. Debe abstenerse cuando corresponda, ser reproducible y mantener decisiones justificables y auditables.

    Casos de prueba mínimos

    Probar escenarios multi-convenio, ambiguos con fallback, imposibles, válidos con respuesta clara y válidos con contexto insuficiente, analizando qué herramientas se ejecutaron y si el agente actuó de forma conservadora o arriesgada.

    Entregables

    Código del agente, logs completos, resultados de pruebas y un breve documento técnico con decisiones de diseño, límites conocidos y errores pendientes.

    Criterio de éxito

    El bloque se supera si el sistema prioriza abstenerse antes que inventar, mantiene trazabilidad clara, actúa como orquestador y produce errores explicables. El foco es fiabilidad, no brillantez.

    Tool 1 · Selección de convenios múltiples. Algunas preguntas afectan a varios convenios, otras son ambiguas o no aplican a ninguno. El sistema debe trabajar en dominio cerrado (solo PDFs existentes), permitir devolver varios convenios o NONE y generar un output estructurado y validable. La clave es decidir cuándo realmente tiene sentido seleccionar más de uno.

    Tool 2 · Recuperación de contexto multi-convenio. Un RAG simple puede mezclar fuentes y sesgar la respuesta hacia un único convenio. Es necesario recuperar contexto por cada convenio, limitar fragmentos por fuente y mantener trazabilidad (PDF y página), equilibrando cantidad de información y ruido.

    Tool 3 · Evaluación de suficiencia. El modelo no distingue bien entre evidencia débil y sólida. Se requiere una métrica explícita, decisión binaria suficiente/insuficiente y capacidad de abortar si no hay base suficiente. El reto es definir qué es “suficiente” en el dominio.

    Tool 4 · Síntesis controlada. El contexto debe entregarse estructurado, con fuentes visibles y preparado para auditoría, evitando mezclas implícitas.

    Tool 5 · Validación final. Para evitar contradicciones o lenguaje inseguro, se necesitan reglas deterministas, posibilidad de invalidar la respuesta y un fallback seguro.
