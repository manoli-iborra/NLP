# ** El LLM como Orquestador**

Durante mucho tiempo, los LLMs se han entendido como sistemas puramente generativos: reciben texto y producen texto. Sin embargo, en entornos profesionales y productivos, este enfoque se queda corto. Un modelo útil no solo debe redactar bien, sino tomar decisiones, acceder a sistemas externos y coordinar acciones de forma fiable. Aquí surge el concepto del LLM como orquestador, apoyado en Tools (Herramientas) y Function Calling (Llamada a funciones).
Una Tool es cualquier componente externo al modelo que le permite interactuar con el mundo real o con sistemas especializados. Puede ser una búsqueda web, una consulta a una base de datos SQL, un script de Python, una llamada a una API corporativa o incluso un sistema de gestión de archivos. La clave es que el modelo no ejecuta la lógica, sino que decide cuándo y cómo debe invocarse esa herramienta para obtener información fiable o realizar una acción concreta.
Este enfoque supone un cambio profundo en el rol del modelo. En lugar de intentar responder a todo usando únicamente su conocimiento interno, el LLM actúa como un sistema de control inteligente que evalúa cada situación antes de actuar. El flujo típico pasa a ser:
- Analizar la intención del usuario, entendiendo si se trata de una pregunta, una acción o una consulta técnica.
- Evaluar si dispone de la información necesaria en su contexto o memoria paramétrica.
- Seleccionar la herramienta adecuada cuando detecta que necesita datos externos o capacidades que no posee.
- Formatear la petición de forma estructurada y precisa para que la herramienta pueda ejecutarse sin ambigüedades.
  
En este modelo, el valor del LLM no reside solo en lo que “sabe”, sino en su capacidad para coordinar recursos, combinar resultados y devolver una respuesta final coherente, verificable y alineada con los sistemas reales de la organización.




## **Mecánica del Function Calling**

El Function Calling no implica que el modelo ejecute código directamente. Un LLM es una red neuronal entrenada para generar texto, no un intérprete ni un entorno de ejecución. Su papel se limita a decidir cuándo es necesaria una función y describir cómo debe llamarse, dejando la ejecución real en manos del sistema que lo rodea.
El proceso técnico se articula en varias fases bien definidas:
Definición: Se le proporciona al modelo un catálogo de funciones disponibles, descritas de forma estructurada. Cada función incluye su nombre, los parámetros esperados, los tipos de datos y una explicación clara de su propósito, de modo que el modelo pueda razonar sobre cuándo utilizarla.
Detección: Al analizar el prompt del usuario, el modelo evalúa si puede responder con la información que tiene o si necesita una función externa. Si decide invocarla, no ejecuta nada, sino que genera una salida en un formato acordado, normalmente JSON o etiquetas XML, que describe exactamente la llamada.
Intercepción: El código que envuelve al modelo, a menudo llamado wrapper u orquestador, detecta ese formato especial. En ese momento se detiene la generación normal, se extraen los parámetros y se ejecuta la función real en el backend o servidor correspondiente.
Inyección: El resultado devuelto por la función se reintroduce en el contexto del modelo como si fuera un nuevo mensaje de sistema o de herramienta, aportándole información fresca y verificada.
Respuesta final: Con ese nuevo contexto, el modelo genera la respuesta definitiva para el usuario, ya no basada en suposiciones, sino en los datos reales proporcionados por la función.
Este mecanismo convierte al LLM en un componente de decisión y coordinación, separando claramente el razonamiento lingüístico de la ejecución técnica.


## **Diseño de Herramientas Seguras y Deterministas**

Cuando un LLM interactúa con herramientas externas, el principal riesgo no es que falle, sino que invente datos plausibles pero incorrectos, como nombres de archivos inexistentes o parámetros fuera de rango. Por eso, el diseño de herramientas no debe delegarse al modelo, sino seguir principios clásicos de ingeniería de software defensiva, donde el modelo es un actor no confiable que hay que acotar y validar.
**El Router de Convenios (PDF Routing)**
En el caso práctico, se introduce un Router como capa intermedia obligatoria. En lugar de permitir búsquedas abiertas sobre todos los PDFs, lo que suele generar ruido y mezclar conceptos de distintos ámbitos, el modelo debe usar una herramienta específica que decide qué documento es el correcto antes de cualquier consulta.
Uso de description.json: Mantener un archivo de metadatos con la descripción de cada PDF, su dominio y su propósito actúa como un verdadero “ancla de realidad”. El modelo no inventa fuentes, solo puede razonar sobre las que existen y están explícitamente descritas.
Dominios cerrados: La herramienta debe aceptar únicamente valores predefinidos. Si el modelo solicita un convenio que no está en la lista, el sistema debe responder con un error controlado o un valor explícito como NONE, evitando búsquedas ambiguas o silenciosamente incorrectas.


## **Diseño de Herramientas Seguras y Deterministas**

Salidas Estructuradas y Validación por Regex
Incluso cuando el modelo decide correctamente usar una herramienta, la salida generada puede incluir ruido textual o desviarse del formato esperado. Para evitarlo, es imprescindible añadir capas de validación estrictas antes de ejecutar cualquier acción.
- **Regex (Expresiones Regulares)**: Permiten extraer de forma precisa el valor relevante, como un nombre de archivo o un identificador, ignorando cualquier texto adicional que el modelo haya generado.
- **Validación de esquema**: Si la salida esperada es un JSON, debe comprobarse que sea sintácticamente válido y que incluya todos los campos obligatorios con los tipos correctos. Cualquier desviación debe provocar un fallo explícito, no una ejecución parcial.
En conjunto, estas prácticas convierten las herramientas en componentes deterministas, predecibles y seguras, donde el LLM aporta inteligencia en la decisión, pero el sistema mantiene el control total sobre qué se ejecuta y cómo.


## **Detección de Ignorancia: El "No sé" como Victoria**

En NLP académico y en sistemas profesionales, una respuesta incorrecta es más dañina que no dar ninguna. Por eso, parte del control de un LLM consiste en enseñarle a reconocer explícitamente sus límites, ya sea mediante Supervised Fine-Tuning (SFT) o a través de prompting cuidadosamente diseñado. Lograr que el modelo diga “no lo sé” en el momento adecuado no es un fallo, sino una señal de madurez del sistema.
**Criterios de Abstención**
Para que el modelo sepa cuándo abstenerse, es necesario definir reglas claras en el System Prompt que prioricen la prudencia frente a la especulación. Algunos criterios habituales son:
- Ambigüedad: Cuando la pregunta puede interpretarse de varias formas y no hay contexto suficiente para desambiguar.
- Cobertura limitada: Cuando la consulta se refiere a un sector, normativa o dominio que no está cubierto por los documentos disponibles.
- Contradicciones: Cuando las fuentes recuperadas contienen información incompatible entre sí y no es posible resolverla de forma fiable.
  
En estos casos, forzar una respuesta solo aumenta el riesgo de error. Elegir NONE o un “No lo sé” explícito preserva la calidad global del sistema.

**Reducción de la Sobreconfianza**

Los LLMs modernos tienden a ser complacientes, es decir, intentan responder incluso cuando no tienen base suficiente. La integración de herramientas ayuda a combatir esta sobreconfianza al separar claramente el razonamiento lingüístico de la obtención de datos. Si una herramienta de búsqueda, una base documental o un router no devuelve resultados válidos, el modelo dispone de una evidencia objetiva de que no puede responder.
Este diseño convierte la ignorancia en una decisión informada, no en una carencia, y refuerza la fiabilidad del sistema al evitar respuestas inventadas o poco fundamentadas.

## **Guardrails y Seguridad del Sistema**

Dotar a un LLM de acceso a herramientas externas aumenta enormemente su utilidad, pero también amplía la superficie de ataque del sistema. En este contexto, amenazas como la inyección de prompts o el uso indebido de funciones dejan de ser teóricas y pasan a ser riesgos reales. Por ello, es imprescindible rodear al modelo de guardrails claros que limiten su capacidad de acción y protejan la infraestructura.
- **Validación de argumentos**: El modelo nunca debe tener la capacidad de enviar directamente comandos al sistema operativo, consultas SQL sin filtrar o llamadas a APIs sensibles. Todos los parámetros generados por el LLM deben pasar por capas de saneamiento y validación estrictas que descarten entradas maliciosas o fuera de especificación.
- **Principio de mínimo privilegio**: Las herramientas expuestas al modelo deben operar con los permisos mínimos necesarios, preferiblemente en modo solo lectura y dentro de un entorno aislado o sandbox. El modelo no necesita acceso completo al sistema, solo a la funcionalidad concreta que resuelve la tarea.
- **Human-in-the-loop**: En escenarios críticos o de alto impacto, el LLM no debe ejecutar acciones directamente. Su rol se limita a proponer una llamada a la función, que posteriormente es revisada y aprobada por un humano o por un sistema de reglas deterministas antes de su ejecución.
  
En conjunto, estos mecanismos transforman al LLM en un componente seguro y controlado, donde la inteligencia está en la toma de decisiones, pero la autoridad final permanece siempre en el sistema que lo gobierna.
