    Entorno de producción¶

    El Abismo entre el Notebook y la Producción¶

    Muchos proyectos de IA fracasan al intentar pasar de un prototipo a un entorno real. En un notebook local, tenemos control absoluto: el script corre en nuestra máquina, solo un usuario lo usa y los datos son previsibles. En producción, el escenario cambia drásticamente y surgen retos críticos:

    • Concurrencia: Múltiples usuarios pueden realizar consultas simultáneamente, lo que requiere que el sistema gestione colas y recursos sin bloquearse.

    • Latencia: Los usuarios esperan respuestas rápidas; segundos extra pueden significar abandono o frustración.

    • Disponibilidad: El sistema debe estar activo 24/7, sin caídas por mantenimiento o errores inesperados.

    • Seguridad: Es imprescindible proteger la API para evitar accesos no autorizados o inyecciones de código malicioso que puedan comprometer el modelo o los datos.

    El salto del prototipo a la producción exige pensar en estos factores desde el diseño inicial, no como un parche posterior.

    Arquitectura de una API de Deep Learning¶

    Para poner nuestro agente en producción, la práctica recomienda exponerlo mediante FastAPI, una solución robusta y flexible para servicios de Machine Learning en Python.

    FastAPI ofrece varias ventajas críticas:

    • Asincronía (async/await): Permite atender múltiples peticiones simultáneamente sin bloquear el servidor mientras el modelo genera respuestas. Validación con Pydantic: Garantiza que los datos de entrada y salida cumplan un contrato estricto, reduciendo errores de tipo y mejorando la fiabilidad.

    • Documentación Automática: Genera una interfaz interactiva (Swagger UI) que facilita probar la API sin necesidad de código cliente adicional.

    Gestión del Ciclo de Vida (Lifespan)

    Modelos grandes y sus índices de búsqueda, como FAISS, consumen mucho tiempo y memoria al cargar:

    Singleton Pattern: El modelo y los recursos asociados deben inicializarse una sola vez al arrancar el servidor, evitando recargas innecesarias que consumen tiempo y VRAM.

    Warm-up: Ejecutar inferencias de prueba al inicio permite que los pesos se carguen en la GPU y evita que el primer usuario sufra latencias extra, asegurando una experiencia fluida desde el primer uso.

    Estos pasos aseguran que el servicio sea robusto, eficiente y escalable, condiciones indispensables para entornos de producción.

    Gestión de Recursos y VRAM¶

    En producción, el factor limitante más crítico para LLMs es la Memoria de Video (VRAM) de la GPU. Los modelos grandes consumen decenas de gigabytes, y sin una gestión cuidadosa, incluso un servidor potente puede quedarse sin recursos, generando errores o ralentizaciones. Por eso es fundamental optimizar tanto la representación del modelo como la manera en que se atienden las consultas.

    La cuantización reduce el tamaño de los modelos y su consumo de VRAM sin sacrificar significativamente la calidad de las respuestas. Esto permite desplegar modelos muy grandes incluso en GPUs con recursos limitados, manteniendo la velocidad y eficiencia.

    La concurrencia es otro desafío clave: si varios usuarios hacen consultas simultáneamente, el sistema debe decidir cómo procesarlas:

    Sequential Processing: Cada petición espera a que la anterior termine, lo que es simple pero muy lento y poco escalable.

    Continuous Batching: Motores de inferencia modernos, como vLLM o Text Generation Inference (TGI), agrupan dinámicamente varias solicitudes en un solo paso de GPU. Esto permite multiplicar el rendimiento sin comprometer la latencia percibida por el usuario.

    El uso combinado de cuantización y batching garantiza que los agentes de LLM sean capaces de atender múltiples usuarios de manera rápida, eficiente y estable en entornos de producción.

    Contenerización con Docker¶

    Muchas veces lo que funciona en local no funciona en producción. Docker permite empaquetar todo el entorno en una imagen portable y reproducible. Esto asegura que el sistema funcione de forma idéntica en cualquier servidor, reduciendo problemas de dependencias o configuraciones inconsistentes.

    Para que Docker acceda a la GPU es necesario instalar el NVIDIA Container Toolkit, que permite al contenedor comunicarse con los drivers de la tarjeta gráfica del host. Además, la imagen base debe ser compatible con la versión de CUDA instalada en el servidor, garantizando que el modelo pueda aprovechar la aceleración por hardware sin conflictos.

    Una imagen de Docker optimizada para NLP y agentes de LLM suele organizarse en capas:

    Base: Sistema operativo ligero con Python y CUDA.

    Dependencias: Instalación de librerías y paquetes del proyecto vía requirements.txt o similares.

    Código del Agente: Copia del código fuente, scripts de orquestación y adaptadores LoRA.

    Exposición de Puertos: Configuración del puerto de la API (por ejemplo, 8000) para que pueda recibir solicitudes externas.

    Esta estructura permite reconstruir la imagen rápidamente y mantener consistencia entre entornos de desarrollo, pruebas y producción.

    Seguridad y Control de Acceso¶

    Los modelos de IA son activos valiosos y costosos; protegerlos es esencial: API Keys: Permiten que solo aplicaciones o usuarios autorizados puedan acceder al modelo, evitando uso no controlado.

    Rate Limiting: Limita la cantidad de consultas por usuario por minuto, previniendo sobrecarga del sistema y ataques de denegación de servicio (DoS).

    CORS (Cross-Origin Resource Sharing): Controla qué dominios web pueden interactuar con la API, evitando llamadas maliciosas desde sitios no autorizados.

    Estas medidas combinadas garantizan un entorno seguro, estable y escalable para el despliegue de agentes de LLM en producción.

    Monitorización y Observabilidad¶

    Tener un modelo desplegado no garantiza que funcione correctamente en todo momento. La monitorización y observabilidad son esenciales para detectar problemas, medir desempeño y alimentar ciclos de mejora continua.

    Logs Estructurados

    Los logs deben ser más que simples impresiones de texto; es necesario registrar información estructurada en formatos como JSON, lo que permite un análisis automático y detallado:

    Tiempo de respuesta (latencia): Cuánto tarda el modelo en generar cada respuesta.

    Tokens generados por segundo: Indicador de rendimiento del motor de inferencia.

    Uso de VRAM: Para prevenir saturaciones de memoria y ajustar cargas de trabajo.

    Feedback del usuario: Si el usuario marca una respuesta como incorrecta o poco útil, se debe registrar la interacción para su posterior re-entrenamiento y mejora del modelo.

    Health Checks

    Endpoints como /health permiten que sistemas de orquestación (por ejemplo, Kubernetes) verifiquen que el modelo está operativo. Estos checks detectan problemas como OOM (Out of Memory) o bloqueos en la inferencia y pueden disparar reinicios automáticos, asegurando disponibilidad constante.

    El Ciclo de Mejora Continua (Flywheel)¶

    La puesta en producción marca el inicio de un ciclo iterativo de mejora, no el final del proyecto. Este ciclo combina monitorización, curación de errores y reentrenamiento para garantizar evolución constante:

    • Producción: El modelo atiende consultas de usuarios reales.
    • Monitorización: Se identifican casos donde el modelo duda, falla o genera respuestas incorrectas.
    • Curación: Los fallos detectados se revisan y etiquetan manualmente para crear datos de calidad.
    • Fine-tuning: El modelo se reentrena con estos datos nuevos para mejorar su desempeño.
    • Evaluación: Se ejecuta el benchmark para asegurar que las mejoras no introducen regresiones.
    • Despliegue: La versión actualizada se publica en la API, reiniciando el ciclo de mejora continua.

    Este enfoque convierte la producción en un motor de aprendizaje constante, asegurando que el agente se vuelva más confiable, eficiente y adaptado a las necesidades reales de los usuarios.

    Práctica 6: Evaluación avanzada de sistemas NLP¶

    Objetivo

    El sistema deja de ejecutarse como script aislado y pasa a funcionar como servicio accesible mediante API. El agente se convierte en una aplicación persistente, con control de acceso, configuración externa y trazabilidad en entorno servidor.

    Stack adoptado

    Se expone una API profesional en Python ejecutada con servidor ASGI y validación estricta de esquemas. El foco está en la correcta exposición del modelo, sin abordar aún la contenerización.

    Contrato de servicio

    Se define un endpoint principal para consultas y otro de salud. Las respuestas siguen un esquema estructurado con pregunta, respuesta, fuentes y metadatos, protegidas mediante API Key en cabecera.

    Gestión de recursos

    El agente se instancia una sola vez al iniciar el servidor y permanece en memoria, evitando recargas por petición y permitiendo atender múltiples solicitudes de forma eficiente.

    Integración del agente

    La clase desarrollada en bloques anteriores se reutiliza directamente como objeto persistente dentro del servidor, manteniendo separación entre lógica y capa HTTP.

    Configuración y seguridad

    Las credenciales y parámetros se gestionan mediante variables de entorno, evitando valores sensibles embebidos en el código.

    Pruebas y manejo de errores

    Se incluye un cliente de pruebas que consume la API como aplicación externa. El servidor captura excepciones y evita exponer errores internos al cliente, dejando registro para auditoría.

    Criterio de éxito

    El sistema está listo cuando responde en tiempos razonables, protege el acceso, maneja fallos de forma controlada y mantiene separación clara entre lógica del agente y exposición del servicio.
